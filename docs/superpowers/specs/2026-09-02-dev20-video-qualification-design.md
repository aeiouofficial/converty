## Goal

Close the qualification gap for Converty's already-existing fixed Video product surface. dev.20 proves the current Video presets through the same packaged product path and failure-isolation standard already established for Audio and Image. It does not introduce a second Video architecture.

## Existing product surface under qualification

### Accepted source extensions

`.mp4`, `.mov`, `.mkv`, `.avi`, `.webm`, `.m4v`, `.mpeg`, `.mpg`, `.wmv`

### Fixed action `video.mp4.h264`

- Output extension: `.mp4`
- Required FFmpeg argument tokens after input:
  `-map 0:v:0? -map 0:a:0? -c:v libx264 -preset medium -crf 23 -c:a aac -b:a 192k -movflags +faststart`
- Required ffprobe result: H.264 video plus AAC audio.

### Fixed action `video.webm.vp9`

- Output extension: `.webm`
- Required FFmpeg argument tokens after input:
  `-map 0:v:0? -map 0:a:0? -c:v libvpx-vp9 -crf 32 -b:v 0 -c:a libopus -b:a 128k`
- Required ffprobe result: VP9 video plus Opus audio.

### Fixed action `extract.audio.mp3`

- Output extension: `.mp3`
- Required FFmpeg argument tokens after input:
  `-vn -c:a libmp3lame -b:a 192k`
- Required ffprobe result: MP3 audio and no video stream.

## Architecture and trust boundary

Preserve the established product path exactly:

`IExplorerCommand DLL -> fixed app-local Converty.Bridge.exe -> strict disposable Converty.EngineWorker.exe / typed provider -> fixed app-local FFmpeg -> private staging -> validated transactional numbered no-overwrite publication`

The qualification harness may invoke the fixed Bridge executable directly for automation, but conversion under test must still execute through the packaged Bridge -> strict worker/provider -> staged app-local FFmpeg path.

Do not introduce:

- shell command construction;
- raw FFmpeg argument pass-through;
- PATH-based converter lookup;
- arbitrary converter/plugin discovery;
- ordinary conversion network dependency;
- silent Strict-to-Compatibility fallback;
- signing private keys in repository/workspace.

## Test fixture design

Every positive Video fixture contains both one video stream and one audio stream so that all three actions are meaningful. Fixtures are deterministic, tiny, development-only media generated by the pinned development FFmpeg before product-path conversion.

Use 64x48 video and a short deterministic duration (approximately 0.25 seconds) to keep Windows CI bounded. Source encodings/muxers should be native to each advertised extension rather than renaming payloads:

- `.mp4`: MP4 container with H.264 + AAC
- `.mov`: MOV container with H.264 + AAC
- `.mkv`: Matroska with H.264 + AAC
- `.avi`: AVI with MPEG-4 video + MP3 audio
- `.webm`: WebM with VP9 + Opus
- `.m4v`: MP4-family muxing with H.264 + AAC, written to `.m4v`
- `.mpeg`: MPEG program stream with MPEG-2 video + MP2 audio
- `.mpg`: MPEG program stream with MPEG-2 video + MP2 audio
- `.wmv`: ASF/WMV with WMV2 video + WMA2 audio

If the pinned development FFmpeg genuinely cannot generate or consume one of these advertised formats, that is product-surface evidence. The test must fail visibly; the harness must not fake success by extension renaming.

## Positive qualification matrix

Run all nine accepted source extensions through all three fixed actions: `9 x 3 = 27` real packaged conversions.

For every case:

1. Copy the deterministic fixture to a case directory using a Unicode/metacharacter filename such as `Hör clip & semi; -dash [x].ext`.
2. Hash the source before conversion.
3. Reserve the unnumbered destination where source and output are not the same path, with sentinel bytes and hash them.
4. For same-extension output/source alias cases (`.mp4 -> .mp4` and `.webm -> .webm`), require publication to choose a numbered output without altering the source.
5. Invoke the packaged Bridge using the typed preset ID and literal filesystem path as independent process arguments.
6. Require Bridge exit `0`.
7. Require source bytes unchanged.
8. Require any pre-existing destination bytes unchanged.
9. Require a non-empty numbered output.
10. Require zero `.converty-*.partial.*` staging residue.
11. ffprobe the published output and require the exact stream/codec contract for the target action.

## Negative qualification

### Malformed input

Create a file with an advertised Video extension and invalid non-media bytes. Run a fixed Video action twice. Both attempts must:

- return non-zero;
- return the same exit code;
- preserve source bytes;
- preserve pre-existing destination bytes;
- publish no numbered output;
- leave no partial staging residue.

### Physically truncated input

Create a valid Video fixture, truncate it to a small prefix that cannot be decoded as the intended media, and run a fixed Video action twice. Apply the same deterministic rejection assertions as malformed input.

## Mixed-batch failure isolation

In one Bridge process, submit this ordered input sequence to `video.mp4.h264`:

1. valid MP4
2. malformed AVI
3. valid MOV
4. truncated MKV
5. valid WebM

Run the batch twice.

For each run require:

- every member is attempted;
- aggregate Bridge exit code is `4` after processing all members;
- valid members before and after failures publish the expected outputs;
- invalid members publish nothing;
- all source bytes remain unchanged;
- all reserved/pre-existing destination bytes remain unchanged;
- no partial staging files remain;
- no orphan `Converty.EngineWorker` or `ffmpeg` process remains after bounded completion.

## Managed characterization

Before relying on the integration harness, add managed tests that pin the existing Video product contract:

- all nine source extensions are supported by the three Video actions;
- `video.mp4.h264` exact token sequence and `.mp4` output extension;
- `video.webm.vp9` exact token sequence and `.webm` output extension;
- `extract.audio.mp3` exact token sequence and `.mp3` output extension;
- paths remain independent FFmpeg argument tokens and no shell executable/token is injected.

This tranche should not need production-code changes to the preset definitions unless RED evidence proves a real mismatch. Qualification-only changes are preferred when existing behavior already satisfies the approved contract.

## Static contract

Add a dev.20 static test that requires:

- both Video harness scripts to exist;
- the acceptance harness to enumerate all nine source extensions and all three target presets;
- the acceptance harness to use `ffprobe` and assert video/audio codec contracts;
- malformed and truncated repeated negative cases;
- Unicode/metacharacter path coverage;
- source/destination preservation and partial-output checks;
- the mixed-batch harness to contain the five-member valid/invalid order, repeat twice, expect aggregate exit `4`, and check orphan worker/FFmpeg cleanup;
- Windows CI to invoke Video acceptance and Video mixed-batch isolation after Image gates and before managed tests.

The static test is written and committed first so CI produces preserved RED evidence before the harness/CI implementation is added.

## Regression and CI ordering

Do not remove or weaken existing gates. Managed Windows CI must continue to run:

- Product Bridge -> FFmpeg smoke
- Audio source/malformed acceptance
- Audio mixed-batch isolation
- Image source/malformed acceptance
- Image mixed-batch isolation
- new Video source/malformed/truncated acceptance
- new Video mixed-batch failure isolation
- managed tests
- deterministic workspace/delivery qualification

## Version and release authority

Behavior/evidence work belongs on the development branch first. The version must become `0.1.0-dev.20` before final dev.20 authority generation.

After behavior qualification is green:

1. curate only non-generated metadata;
2. generate source SBOM, release SBOM, package manifest, and SHA256SUMS in ordinary CI;
3. independently verify generated-authority artifact digest, CRC, exact four-file member set, and version;
4. synchronize generated authority only through the guarded exact-parent self-deleting authority workflow;
5. require generated-authority zero-diff and complete deterministic Windows workspace/delivery qualification;
6. re-read live `main` immediately before promotion;
7. non-force fast-forward only if `main` is still the expected base and the candidate is a strict descendant;
8. run fresh exact-main continuity + static + managed CI on the promoted SHA;
9. independently verify exact-main workspace and delivery artifacts;
10. re-read live refs before declaring dev.20 frozen.

A green side branch alone is not release authority.

## Out of scope

Do not add in dev.20:

- new Video action IDs;
- Copy/Remux/Transcode planning or optimization;
- hardware acceleration;
- HDR policy;
- subtitle policy expansion;
- metadata-policy expansion;
- wider converter/plugin trust surfaces.

Full B8 Copy/Remux/Transcode planning remains a later tranche.

## Completion criteria

dev.20 can be declared frozen only when all approved Video qualification requirements are green on the exact promoted `main` SHA, generated authority is synchronized and zero-diff, deterministic workspace/delivery evidence is independently verified, and Slack/Drive/GitHub documentation plus the recursive OPEN handover are reconciled.

Converty remains not generally ship-ready after dev.20 because production FFmpeg provenance/redistribution, production signing/MSIX, headed Windows 11 Explorer acceptance, security/fuzz/chaos, and end-user gates remain open.
